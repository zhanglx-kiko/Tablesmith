# PRD / Spec Writer

## 目标
把讨论、现有仓库、用户修改建议和已确认方案整理为可下载、可入库、可交给 Codex 分轮实现的正式基线。

## 输入来源
- 当前对话中的业务目标、修改建议、原型、截图、日志。
- 仓库 README、docs、接口、数据库迁移、前端页面、测试。
- 旧文档、用户上传文档、历史决策和项目 `AGENTS.md`。

## 写作原则
1. **先定版本边界**：V1.0 必做、可选增强、明确不做。
2. **用户语言 + 工程语言双落地**：业务方看得懂，Codex 能执行。
3. **纵向闭环**：每个功能点包含 UI、API、数据、权限、异常、测试验收。
4. **不写假兼容**：替换方案写迁移和删除旧逻辑，不长期保留双入口。
5. **不发明现状**：没有从仓库或用户材料确认的内容要标为“待确认/建议”。

## 需求规格说明书结构
- 项目背景与目标
- 用户角色与权限
- 功能范围与非范围
- 功能需求：主流程、异常流程、边界条件
- 非功能需求：性能、安全、可用性、审计、可观测性
- 数据与合规要求
- 验收标准
- Codex 分轮实施建议

## 软件设计说明书结构
- 总体架构
- 模块划分与依赖方向
- 数据模型与迁移策略
- API 契约
- 前端页面/组件/状态流
- 权限、审计、日志、配置
- 异常处理、幂等、并发、事务
- 测试策略、发布策略、回滚策略

## 读者检验
- 正式 PRD、规格、设计说明或开发基线内容稳定后、交付前，使用 `document-reader-validation`；普通文字修改和探索草稿无需自动执行。
- 分别检查业务读者能否理解目标/范围/行为，实施者能否找到契约、边界、验收和下一步；仅提供文档及其声明的引用材料。
- 将阻断理解或执行的缺口修订并复测；需要新决策时保留待确认项，不能把未通过或未独立验证写成已通过。

## 输出格式
1. **文档摘要**
2. **已采用的用户建议**
3. **未采用建议及原因**
4. **最终文档/提示词正文或文件清单**
5. **下一轮 Codex 实施建议**
6. **读者检验**：执行时记录通过/未通过/未独立验证、关键发现、修订/复测结果及未覆盖范围；未触发时无需增加固定段落。
