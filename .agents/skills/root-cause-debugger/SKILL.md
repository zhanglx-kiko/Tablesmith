# Root Cause Debugger

## 目标
建立可复现事实链，证明根因，再做最小有效修复；不靠猜测批量乱改，不用跳过测试、吞异常、扩大兼容分支来掩盖问题。

## 适用场景
- 用户给出错误截图、日志、接口失败、页面异常、CI 失败、线上告警，但根因未知。
- flaky test、性能退化、并发/时序/缓存/环境差异问题。
- 最近改动后前后端/API/权限/数据不对齐。
- 需要跨仓库、跨服务、跨 UI 与后端链路定位。

## 插件/工具联动
以下名称表示可选联动能力，不代表当前环境一定安装。先确认工具是否可用；不可用时使用本地命令、项目日志、测试夹具或浏览器基础能力完成同等证据收集，并明确记录未执行的插件步骤。

根据问题来源先建立证据入口：
- **GitHub CI / PR 失败**：优先使用 `gh-fix-ci` 或 GitHub 工具抽取失败 job、日志、commit、diff，再进入假设树。
- **PR 评论要求修改**：结合 `gh-address-comments`，先归纳评论中的真实问题，再定位。
- **UI / 浏览器 / E2E 问题**：优先使用当前会话提供的 computer-use、Playwright、截图或其他浏览器工具建立可重复路径；先确认能力可用，不把固定工具名当作必备入口。
- **线上错误**：优先使用 `sentry` 或可用日志平台获取 stack trace、release、环境、用户影响面。
- **安全扫描发现**：使用当前会话提供的安全扫描或审查工具；没有专用工具时，用本地扫描器、依赖报告、测试复现或代码证据证明触发条件再修。
- **本地 Windows 命令异常**：配合 `windows-powershell-runner` 排除 shell、编码、路径和 PowerShell 版本差异。
- **资源残留导致失败**：配合 `dev-resource-cleanup` 检查端口、后台进程、浏览器会话、缓存污染。

## 流程
### 1. 收集现象
- 失败命令、错误堆栈、日志、HTTP 状态、截图、用户操作路径。
- 发生频率：必现、偶发、特定环境、特定数据、特定时间。
- 最近变更：代码、配置、依赖、数据库、部署、外部服务。
- 影响范围：单测、集成、前端、后端、生产链路、特定用户。
- 与用户描述不一致时，用具体证据澄清，不直接否定用户。

### 2. 建立反馈环
优先使用失败测试、新增回归测试、curl/HTTP 脚本、CLI/脚本复现、Playwright/浏览器复现、最小 harness。反馈环必须能判断：
- 修复前失败；
- 修复后通过；
- 能覆盖用户描述的触发路径。

没有现成反馈环时，先构造最小复现，不要直接大改。

### 3. 假设树
列 3-5 个可证伪假设，再逐一验证：
- 输入/数据异常；
- 状态污染或缓存；
- 测试顺序或隔离问题；
- 并发竞态；
- 依赖版本；
- 环境变量或密钥缺失；
- 平台差异；
- 时间/时区/随机性；
- 最近提交或契约漂移。

每个假设都要有验证动作和证据，不保留没有证据的猜测。

### 4. 根因证明
说清：
- 哪段代码/配置/数据导致问题；
- 触发条件是什么；
- 为什么它能解释全部现象；
- 为什么原有测试没覆盖；
- 为什么排除了其他主要假设。

### 5. 修复规则
- 只改根因相关代码，不扩大范围。
- 不通过跳过测试、吞异常、扩大 timeout、放宽断言、增加无意义兼容来掩盖问题。
- 临时 debug 日志必须有唯一标记，结束前删除。
- 修复必须补回归测试；没有测试缝隙时说明原因并给出替代验证。
- 前后端/API/权限/文档受影响时，转入 `ui-backend-contract-sync`。
- 发布、配置、数据库或缓存受影响时，转入 `release-readiness-rollback`。

## 输出格式
1. **现象**
2. **证据来源/插件联动**
3. **反馈环/复现方式**
4. **假设与排除过程**
5. **根因**
6. **修复**
7. **回归测试**
8. **验证结果**
9. **仍需观察**
