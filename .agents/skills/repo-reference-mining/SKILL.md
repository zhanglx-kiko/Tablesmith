# Repo Reference Mining

## 目标
让 Codex 在开发前先读取当前仓库和用户指定参考项目，合理借鉴成熟实现，避免新建平行架构、重复造轮子、偏离项目风格或破坏既有约束。

## 读取顺序
1. 先读当前仓库：`AGENTS.md`、README、docs、目录结构、核心模块、测试、配置模板、最近相关实现。
2. 再读用户本轮明确指定的参考项目、参考目录、参考文件或开源实现。
3. 如果 `AGENTS.md`、`CONTEXT.md`、项目文档中声明了参考目录或基线项目，必须读取并说明借鉴关系。
4. 如果参考路径不存在或无权限读取，说明尝试路径和影响，不要凭空声称已经参考。

## 默认规则
- 能照搬成熟实现就照搬，但必须适配当前项目命名、架构、依赖、安全规则和错误处理风格。
- 优先借鉴同仓库同模块已有模式，其次是同组织参考项目，最后才是通用开源做法。
- 不得修改、删除、破坏参考项目。
- 不得提交参考项目中的真实密钥、私有配置、临时文件、客户数据。
- 不把参考项目的 demo 代码、过时依赖、弱安全默认值原样搬进当前项目。

## 重点检查
- 模块边界、分层方式、依赖方向、包命名、异常处理。
- API 风格、错误码、权限注解、分页排序、审计字段。
- 数据库迁移、索引、软删除、多租户、数据权限。
- 前端页面结构、组件复用、状态管理、路由、权限按钮、API client。
- 测试组织、fixture、集成测试、E2E、mock 使用边界。
- 部署脚本、配置读取、健康检查、日志规范、资源清理。
- 文档结构、命名口径、交付清单、验收报告。

## 借鉴判定
- **直接借鉴**：同一技术栈、同一问题域、契约相近、风险低。
- **改造借鉴**：模式有价值，但命名、依赖、边界、权限或配置需要适配。
- **不采用**：与当前架构冲突、引入过重依赖、过期、不安全、只是 demo、缺少测试或不可维护。

## 输出要求
必须说清：
- 读取了哪些当前仓库文件；
- 读取了哪些参考文件/目录；
- 借鉴了什么具体模式；
- 未采用什么及原因；
- 当前项目做了哪些适配；
- 是否发现敏感信息，如何处理。

## 与其他 skills 协作
- 参考实现涉及前后端/API 字段时，联动 `ui-backend-contract-sync`。
- 参考实现涉及安全、配置、密钥时，联动 `security-secret-config-guard`。
- 参考实现涉及发布、DB migration、灰度时，联动 `release-readiness-rollback`。
- 参考实现只是定位问题证据时，联动 `root-cause-debugger`。

## 输出格式
1. **读取的当前仓库文件/目录**
2. **读取的参考文件/目录**
3. **可借鉴点**
4. **未采用点及原因**
5. **当前项目适配规则**
6. **敏感信息处理说明**
