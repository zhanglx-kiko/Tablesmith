# Release Readiness & Rollback

## 目标
确认改动可发布、可观测、可回滚或可前滚修复，不破坏数据安全和关键链路。对数据库、配置、安全、缓存、权限、协议、部署脚本类改动，必须先有发布与回滚判断。

## 发布影响面
检查：
- 用户可见行为、管理端行为、批处理/定时任务、异步任务。
- API/SDK/CLI、网关、Nginx、路由、协议、文件上传下载。
- 数据库 schema、索引、迁移、回填、约束、默认值、触发器、视图。
- 消息队列、cron、缓存 key/TTL/失效策略、搜索索引。
- 配置、密钥、权限、网络策略、跨域、证书。
- 第三方依赖、镜像、Docker Compose/K8s、部署脚本。
- 日志、监控、告警、审计、数据导入导出。

## 兼容策略
- 内部重构默认不保留兼容旧入口。
- 生产多版本并存、数据库 expand-contract、外部公共 API 才允许临时兼容。
- 每个兼容点必须写明：原因、风险、关闭条件、删除计划。
- 不允许用永久兼容掩盖前后端/API/文档未同步。

## 数据库迁移标准
只有涉及持久化数据、生产多版本并存或不可逆数据操作时，才进入下面的 expand-contract、回填和校验流程。纯应用发布、文案、无状态配置或仅开发环境的一次性迁移，应记录适用性判断并执行与风险匹配的轻量验证，不要套用完整数据库迁移清单。

涉及生产数据库的变更优先采用 expand-contract 思路；若明确是纯开发环境或用户确认可停机，应记录理由并选择与风险匹配的迁移策略：

### 1. Expand
- 先新增可空字段、表、索引、兼容读取逻辑或新约束的安全前置条件。
- 大表加索引要评估锁表、并发写入、磁盘、回滚成本。
- 新字段默认值、NOT NULL、唯一约束要分阶段处理。

### 2. Dual read/write 条件
- 多版本并存时，明确是否需要双写、双读、读新回旧、读旧补新。
- 每个双读/双写点必须有开关、指标和删除计划。
- 不需要兼容时，明确说明为什么可以直接切换。

### 3. Backfill / 回填
- 回填必须支持 dry-run、分批、幂等、断点续跑、失败重试。
- 每批记录数量、排序键、过滤条件、重试策略要明确。
- 回填日志不得输出敏感数据。

### 4. 校验 SQL
发布前后需要准备校验 SQL 或等价脚本，例如：
- 行数一致性；
- 空值/非法值检查；
- 唯一性/外键一致性；
- 新旧字段对比；
- 回填进度和失败记录。

### 5. Contract
- 确认所有服务、前端、脚本、报表、导出、测试都不再依赖旧字段/旧表/旧接口后，再删除。
- 删除前必须全仓扫描旧契约并确认生产无旧版本依赖。

### 6. 不可逆变更
- 删除数据、压缩历史、字段类型收窄、枚举收窄、不可逆加密、外部系统同步等不可逆变更必须有前滚补偿方案。
- 不能承诺“可回滚”时，要明确只能前滚修复，并列出补偿步骤。

## 灰度策略
根据风险选择：
- 本地/测试 smoke；
- 预发验证；
- 内部用户/小流量灰度；
- 按租户/区域/用户/比例/功能开关放量；
- 影子流量、双读对比、双写校验；
- 只读验证窗口。

## 监控与告警
至少考虑：
- 错误率、延迟分位数、吞吐、CPU、内存、磁盘、连接池。
- 队列积压、重试率、死信、定时任务成功率。
- 业务成功率、数据一致性、迁移进度、回填失败数。
- 登录/权限/支付/上传下载等关键链路指标。
- 日志不能泄露敏感信息。

## 回滚/前滚
明确：
- 触发条件和停止放量条件；
- feature flag 关闭方式；
- 应用回滚步骤；
- 数据库是否可逆；
- 不可逆时的前滚补偿；
- 回滚后验证命令/指标/通知对象；
- 旧版本是否兼容新 schema。

## 输出格式
1. **发布影响面**
2. **兼容性结论**
3. **数据库迁移方案**
4. **灰度计划**
5. **监控与告警**
6. **回滚/前滚方案**
7. **发布前清单**
8. **最终建议**
