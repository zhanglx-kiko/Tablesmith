# Requirement Grill With Docs

## 目标
通过“查现状 + 追问 + 推荐答案 + 文档沉淀”把模糊需求变成 Codex 可执行的开发基线。

## 先查再问
能从仓库判断的问题，不问用户；先读取：
- `AGENTS.md`、README、docs、接口文档、数据库迁移、测试。
- 已有页面、Controller、DTO/VO、类型定义、配置模板。
- 用户提供的原型、截图、日志、补充方案。

## 追问原则
- 一次只问会影响实现方向的问题。
- 每个问题都给默认推荐答案和原因。
- 轻微不确定不阻塞推进，可在方案中列为假设。
- 对模糊词立即收敛：例如“账号/用户/成员/客户”、“删除/下架/禁用/归档”。

## 追问清单
- 文档读者与用途：谁会读、读完应能决定或执行什么、可假定哪些前置知识；先从材料推断，确有歧义再问。
- 角色与权限：谁能看、谁能改、谁能审批、谁能导出。
- 状态机：状态、流转、撤销、删除、失败、重试、审计。
- 数据归属：哪个服务、哪些表、跨服务同步、历史记录。
- UI 交互：入口、列表、详情、弹窗、空态、错误态、加载态。
- API 契约：路径、请求、响应、错误码、分页、排序、幂等。
- 非功能：性能、并发、数据量、安全、可观测性、回滚。
- 不做什么：明确本版本 out of scope。

## 文档沉淀
- `CONTEXT.md` 只写领域词、概念关系、禁用同义词，不写实现细节。
- ADR 只记录难逆转、非显而易见、有真实取舍的决策。
- 需求文档写用户可见行为；设计文档写模块、接口、数据、权限、测试、部署。
- 需求/设计文档注明目标读者、预期行为和必要引用材料；形成正式基线时接 `prd-spec-writer` 与 `document-reader-validation`，探索阶段不反复做冷读检验。

## 输出格式
1. **已确认结论**
2. **仍需确认的问题**：按阻塞程度排序，并给推荐答案。
3. **建议写入文档的位置**
4. **Codex 可执行边界**：下一轮可开发 / 暂不开发。
